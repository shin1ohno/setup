# Headless `claude` CLI (non-interactive `claude -p`)

Load when a cookbook or script invokes the `claude` CLI non-interactively — a daemon, CI job, systemd/launchd service, or any `claude -p` not driven by a human terminal. Two version/mode-specific behaviors bit two different components in one session; both recur on any headless deployment.

## Auth is `claude setup-token` → `CLAUDE_CODE_OAUTH_TOKEN`, NOT a stored login

`claude setup-token` mints a **long-lived** token for headless/automation use. It is consumed via the env var **`CLAUDE_CODE_OAUTH_TOKEN`** (or a file holding it), NOT stored as an interactive login. Consequences:

- **`claude auth status` reports `loggedIn:false`** even when the token is set correctly and `claude -p` works. So an auth-presence GATE must check the **token env/file** directly (`test -s <token-file>`), never `claude auth status`.
- **Exit-code trap**: `claude auth status` exits `1` when logged out — but piping it through `head` (`claude auth status | head`) swallows the non-zero exit (`head` returns 0), masking the failure inside an `&&` / `only_if` chain. Read `${PIPESTATUS[0]}`, or don't pipe.

Wire the token into a systemd unit as a second, optional EnvironmentFile so a missing token before `setup-token` doesn't hard-fail:

```
EnvironmentFile=/opt/<svc>/memory-v2.env
EnvironmentFile=-/opt/<svc>/keeper-claude.env   # CLAUDE_CODE_OAUTH_TOKEN, mode 600, leading '-' = optional
Environment=HOME=/root
Environment=CLAUDE_BIN=/root/.local/bin/claude
```

Gate timer/service activation on the token file existing, not on `claude auth status`.

## `--mcp-config "{}"` is rejected on claude >= 2.1

`claude -p … --strict-mcp-config --mcp-config "{}"` fails with `Invalid MCP configuration: mcpServers: expected record, received undefined` on claude >= 2.1. Use `--mcp-config '{"mcpServers": {}}'` (empty servers = no tools, the pure-inference contract). Verify `claude --version` before reusing an older example verbatim — capability claims are values, probe them.

## Do NOT copy `~/.claude/.credentials.json` between hosts

An interactive login's `~/.claude/.credentials.json` holds `accessToken` + `refreshToken` + `expiresAt`; the **refresh token rotates on use**, so two hosts sharing one copied file silently invalidate each other (whichever refreshes second gets logged out). The correct mechanism is an **independent `claude setup-token` (or login) per host** — same account, separate token pair, no rotation conflict. See the credential-sharing probe in `~/.claude/rules/debugging.md`.

Origin: 2026-07-04 memory-v2 keeper on CT119 — `setup-token` token surfaced `loggedIn:false`; a `| head` masked `auth status` exit 1; `--mcp-config "{}"` errored on claude 2.1.201; the plan's "copy subscription creds" was corrected to a separate `setup-token` after probing the token structure.

## Runner death detection — 4-layer self-defense

A scheduled/headless `claude -p` runner (a launchd/cron/systemd-timer loop) needs 4 layers of self-defense:

1. **Success is a positive gate: summary marker in the LAST assistant message** — a run whose session output is ONLY「Not logged in · Please run /login」is a *failed iteration*, not a completed one. More generally: process exit 0 / transcript existence / "some assistant output" / no-terminal-error-grep-hit are NOT evidence of success. Gate iteration success on a whitelist condition — the final assistant message contains the summary marker the runner prompt mandated (the prompt must instruct「完了時は必ず <MARKER> を最終メッセージに出力」; gate and prompt instruction are one contract). Observed death shapes that all counted as "success" under a naive runner (which advanced last-success unconditionally and always exited 0): prompt queued but zero assistant entries (×3 sessions), `Connection closed mid-response` mid-death, a 6-token "(no content)" end_turn, and a no-output death right after the skill-load tool_result. Same principle as `rules/sub-agents.md` "Auto-Launched Review Agent": completed = findings RETURNED, never session end. With token auth, gate on the token file per the section above (`test -s <token-file>`), never `claude auth status`.
2. **Grep the session output for terminal errors** — `monthly spend limit` is unrecoverable (waits on the monthly reset / an admin), so create a DISABLED sentinel + notify once and stop the loop itself (restarting every cycle is pure waste). Add `Failed to authenticate: OAuth session expired` and `API Error: 401 Invalid authentication credentials` to the terminal list — auth expiry does not self-heal, so treating it as transient re-burns every cycle until a human re-auths (observed under setup-token operation too, 2026-07-23). `Request timed out` / `Connection closed` are transient, so back off via a sentinel + timestamp (skip a few cycles, then auto-resume).
3. **Deterministic pre-gates (gh/jq probes) are fail-closed, WITH a deadline** — if a probe returns an empty string or an error, SKIP that cycle. A fail-open shape ("unknown, so let the LLM decide") is banned (measured: a fail-open gate wasted 35 of 51 launches on needless opus sessions; a probe-failure fall-through launched with "attendable=unknown"). In bash, `[ -n "$x" ] && [ "$x" = "0" ]` is the classic fail-open — write `[ "$x" = "0" ] || [ -z "$x" ]` so a failure falls to the skip branch. Fail-closed assumes the probe RETURNS — give critical-path gh/jq probes an explicit deadline and treat overrun as probe failure (a 17-minute `gh pr list` hang was observed). macOS runners lack `timeout(1)` by default (exit 127 — see rules/shell.md's external-command audit): use portable means (curl `--max-time`, `GH_REQUEST_TIMEOUT`, gtimeout) in the runner shell. Pair fail-closed with a "notify once after N consecutive skips" so a permanently-broken probe does not silently skip forever.
4. **Watchdog/stall judgment reads the transcript, not the wall clock** — judge stall by the transcript JSONL's last-entry timestamp/mtime, never by time-since-launch: API queue delays of 10–66 minutes to first token (5 sessions) and a mid-session 55-minute API stall were observed, so a launch-based watchdog kills healthy queued runs AND detects real stalls late. Kill only after 2 consecutive no-activity probes on the transcript, reading the tail first to classify stuck-vs-recovering — same principle as `rules/sub-agents.md` "Background Agent Progress Tracking" #4, implemented on the runner-shell side.

Origin: 2026-07 zp-issue-loops audit — an 8-line「Not logged in」-only session counted as completed (a83e457b); the loop restarted every minute after hitting the spend limit (947df123); a fail-open gate wasted 35 of 51 launches on empty opus sessions. Extended 2026-07-24 (claude-md-audit, 238 sessions): 4 death shapes silently counted as success; OAuth-expiry loop-burn; 10–66 min queue delays; 17-min probe hang. Supported by 24+ sessions.

## Healthy human-gated terminal states — close deterministically, notify once, pre-gate on actionability

A loop can reach a state that is NOT an error but cannot be advanced by the LLM (e.g. merge-ready but merge denied). Handling order:

0. **Prefer a deterministic runner-shell action** that closes the state (e.g. the runner's own merge sweep — the runner shell is outside claude's permission system). Make its filter cover the WHOLE class: a branch-prefix filter that misses manually-named branches leaves those PRs permanently human-gated (observed: 50+ full LLM runs re-derived the same merge-ready conclusion over ~19h because the sweep only matched `zp/issue-*` branches).
1. **If truly human-only, notify ONCE from the RUNNER** (not from inside claude) with the full executable command (e.g. `gh -R <repo> pr merge <n> --merge --delete-branch`), deduped by a state key (PR number + head SHA) persisted in a sentinel — same shape as a GPG_NOTIFIED sentinel. A `!` command printed into a headless transcript is NOT notification: nobody reads it in real time.
2. **Sentinel-based cycle skip is allowed only AFTER an actually-observed DENY for that state key** — skipping on a recorded claim alone is the self-fulfilling stale-block pattern (§Permission reality #4 attempt-first still applies; observed: 50+ runs skipped the merge attempt citing a recorded block while the one run that attempted succeeded immediately).
3. **The pre-gate probes for ACTIONABLE work, not object existence** — "an open PR exists" re-launches the LLM every cycle even when nothing changed; probe for unresolved threads / failing checks / head-SHA or mergeStateStatus changes instead.

## Permission reality — probe at design time, re-probe each run (do not normalize the observed matrix)

1. **Design-time probe (once)**: before designing a headless mutation loop (one that unattended-issues push / pr create / merge / label / notify), read `permissions.disableBypassPermissionsMode` in `/Library/Application Support/ClaudeCode/managed-settings.json`. If it is `"disable"`, `--permission-mode bypassPermissions` is inert and the headless run executes in the default mode (`ask` = immediate block with no approver present). In that case, measure each mutating command the loop issues from a REAL headless `claude -p` run, one command at a time, before unattending it — success in an interactive session is not evidence (a human approval is transparently supplied). One e2e marker issue / one dry-run pass is the minimum-cost probe. A gated command's alternative can live in the runner shell OUTSIDE claude (the launchd/cron bash) — the runner is outside claude's permission system.
2. **The matcher is sensitive to the issued form (fairly durable harness behavior, but re-confirm)**: an allowlist `Bash(git status:*)`-style prefix matcher is a string prefix match and does NOT match `git -C /path status`. Because `git-commit.md` mandates the `git -C <absolute-path>` form, write the headless allowlist in the exact form the loop issues (with `git -C`). Gating of `$()` substitution / `&&` compounds / multiline `-m` is content-specific (some PASS, some go to approval) — do not assume blanket "compound = blocked" or "single = allowed"; probe the exact form you plan to issue.
3. **Write-probe the hand-off file**: some versions write-guard everything under `~/.claude/` in a non-bypass session (Write / heredoc / printf all denied, observed — but version-dependent; it has succeeded in other periods). Write-probe the hand-off file once at design time; if denied, place it under the repo's `.git/` or the scratchpad.
4. **A recorded PASS/DENY matrix is a snapshot**: on the same machine, a 2026-06 DENY ceiling (`gh api graphql` / `gh pr merge`) flipped to PASS by 2026-07-06. Keep the detailed matrix in project memory (e.g. zp-SHIN `zp-pr-attend-headless-perms`), update it per run, and do NOT freeze it into this doc. Never skip a satisfied merge gate because a prompt or memory says "blocked" — attempt first, observe the DENY, then escalate. **Exceptions (live instruction ≠ stale snapshot)**: attempt-first applies to rationale-free snapshot records only. (a) A block recorded WITH its design rationale (rules/git-commit.md's kouzoh exception; CLAUDE.md Progress-ledger's "recorded WITH design rationale" case — e.g. merge deliberately delegated to the runner's deterministic shell sweep), and (b) a block the CURRENT run's prompt/runner note declares explicitly with rationale, are live instructions — do not attempt against them. **Precedence for contradictions**: when the live prompt says both "do X" and "X is blocked", read the blocked note as a deny forecast (a deny is expected — not a failure, not needs-human) and resolve by attempting ONCE; skip only when the prompt forbids the attempt itself. Observed: the Goal+NOTE contradiction split identical runs into attempt→deny / attempt→success / skip — remove the contradiction at its source (one sentence in the runner prompt) rather than normalizing any one behavior.

## Notification channels — inline osascript is unreliable under launchd

Do not rely on `osascript -e 'display notification …'` from a launchd-started headless `claude -p` — depending on GUI (Aqua session / Notification Center) reachability it fails with `0:20: syntax error: A identifier can't go after this identifier. (-2740)`. This is NOT a quoting bug: the minimal form `display notification "test"` fails at the same position, and rewriting to a `.scpt` file or stdin form fails identically — while the SAME machine's other runs exit 0 (non-deterministic channel). So: do NOT enter a rewrite/debug loop (observed: ×6 retries in one session, ×14 hypothesis iterations in another) — treat it as best-effort, one attempt, then move on. Durable escalation records (issue/PR comment + `needs-human` label) are the primary channel; if real-time notification is needed, delegate to a runner-shell helper OUTSIDE claude (Slack webhook / terminal-notifier) and fire-test it in a real headless run once at loop-design time. Skills that carry notification steps must state this rule in SKILL.md itself — a headless run loads the skill, not this on-demand doc. Origin: 2026-07-06〜23 zp-pr-attend / zp-issue-resolve — inline, minimal, and file-based forms all -2740 (8 attempts across 3 sessions on 07-23), other runs exit 0.

## Re-dispatch dedup — prior-run artifact probe and runner-side gates

Duplicate re-execution after a re-dispatch is primarily a RUNNER defect — fix it there first:

- **The runner must not destroy work products until push/PR-create success is confirmed.** Do not reset/remove the worker worktree or delete the hand-off file while a push retry is the correct recovery (observed: an SSH-identity failure failed the push, the runner recreated the worktree from origin/main, and the re-dispatched worker — whose branch probe now found nothing — redid 21 minutes of work from scratch). Recovery for a failed push is retrying the push of the EXISTING commit, not a fresh LLM dispatch.
- **The dispatch dedup gate is deterministic, fail-closed, and includes a LOCAL probe**: `test -s` + mtime freshness on the hand-off file. A gate built only on open-PR / start-comment lookups is disabled by the same network outage that caused the push failure (observed: push failure and comment-send failure shared one outage, erasing every gate signal at once).
- **Worker side**: a re-dispatched worker probes prior artifacts BEFORE editing — hand-off file (`test -s` + head), commits ahead of origin/main on the branch, the issue's start comment, in that order (local first). If fresh artifacts exist: verify and reuse, or report "previous run completed; runner-side push failed" in one line and exit. Embed this state-check at the TOP of the runner prompt (same shape as CLAUDE.md's Stale wakeup guard).
- **A prompt's skip list is exhaustive**: when the runner prompt lists skill steps to skip, do not collaterally skip UNLISTED steps — especially the start comment, which is the only dedup breadcrumb that survives a worktree reset (run1 silently extended a Step-0/3 skip to the start comment, erasing the duplicate-detection trail for run2). A prompt that skips Step 0 (issue selection) must still keep Step 0's dedup checks (start comment / linked-PR probe) explicitly alive.

Origin: 2026-07-07 zp #68 — push failed on a missing SSH identity, runner recreated the worktree, run2 redid the entire issue (21 min); the network outage had also erased the comment breadcrumb.
