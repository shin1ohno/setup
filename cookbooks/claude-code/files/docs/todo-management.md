# TODO Management — Capture Routing, Stores, Collect / Reconcile Loops

Load when: creating or saving a TODO (any "あとでやる" / deferred work / personal task), answering "open な TODO は?" / "TODO 見せて", running `/todo-collect` or `/todo-reconcile`, or deciding where a captured item belongs.

Designed 2026-07-06 (E2E discussion). Decisions locked there: TODO.md and issues stay **parallel** (no promotion machinery); reconcile is a manual weekly skill (cron later, if ever); personal tasks are in scope; evidence-based auto-close. The "cron later" branch was taken on 2026-08-17 for the WORK half only — both loops now run on a timer on sh1-cloud (see Cadence below); the personal half stayed manual because its two dependencies live on air.

## Stores (sources of truth)

| Store | Scope | Lifecycle |
|---|---|---|
| `<repo>/TODO.md` | repo-scoped actionable work | entry deleted in the resolving commit (existing CLAUDE.md rule) |
| ai-memory `tags:["todo"]` | personal / cross-project / no-repo | `forget(id)` on completion; weekly reconcile is the backstop |
| memory-work `tags:["todo"]` | WORK no-repo TODOs (Mercari) | same; work data never routes to personal ai-memory (egress rule in `knowledge-persistence.md`) |
| GitHub / zp issues | execution queue for autonomous loops | existing close protocols (self-heal / zp loops) |

**Enumeration is only complete when the count says so**: a memory store is read with `browse(filters: {tags: "todo"}, limit: N)`, and `browse` has no cursor — omit `limit` and the server's default of 50 truncates the answer silently. Always pass `limit` and compare the returned count against the response's `total` (`truncated: true` means they differ). A truncated enumeration is a THIRD state, distinct from a store that could not be reached (`未列挙`) and one that answered empty (`0 件`): record it as `truncated 残数` and never collapse it into either, because both a dedup pass and a completion check read "absent" as "gone". Same silent-cap rule the Slack sweep already follows.

**Federation principle**: issues and TODO.md are NEVER copied into memory. `list` / `reconcile` enumerate them at read time (`gh search issues --assignee=@me --state=open`, `ls ~/ManagedProjects/*/TODO.md`). The collector copies only *raw captures* (unstructured marks). Copying store-to-store creates split-brain.

## Capture routing

Routing is Claude's job — the user just utters intent ("これ TODO にして", "あとでやる"). Applies equally to Claude-created TODOs (deferred work, Known-Limitation rule, review out-of-scope findings).

1. Repo-scoped actionable work → that repo's `TODO.md` (description / reason / concrete first step)
2. Fleet observable anomaly → self-heal path (ES state → issue)
3. Work (Mercari) task → `zp-issue-create` if issue-ripe, else memory-work `remember(content, type='fact', tags=['todo'])`
4. No-repo / cross-project / personal → ai-memory `remember(content, type='fact', tags=['todo'])`

**Contract (all stores)** — every TODO records:

- 完了条件 (close condition; machine-probeable form preferred — "file X exists", "PR merged", "issue closed")
- 対象 (target: repo / host / person / thing)
- 想定 class, or for personal tasks: due date / trigger condition

**Receipt rule**: after every capture, echo one line — destination + close condition ("→ memory (tags:todo) に保存。完了条件: X"). Mis-routing gets corrected on the spot because this line exists.

**Never** write TODO-shaped content to memory without `tags:["todo"]` + a close condition — untagged TODOs are un-enumerable and rot (origin: `Create rules/async-workflows.md` fact sat 6 weeks unsurfaced, found 2026-07-06).

**Mobile / out-of-session**: claude.ai chat with the memory connector is a first-class capture path — "TODO: 〜" → `remember(tags:['todo'])`, same store, no collector involved.

## Surfacing — 4 channels

1. **Contextual**: conversation-start `recall` (existing doctrine) surfaces topically-relevant todos for free — mention them: 「関連する open TODO があります: …」.
2. **Instant list**: 「TODO 見せて」 → `/todo-reconcile` list mode (no probes; `todo_queue.py summary` + current repo TODO.md + both memory stores + federated issues, grouped by theme).
3. **Queue + run logs** (`~/.claude/todo/`, see "Queue" below): `candidates.jsonl` is the O(open) approval queue regenerated by every collect run; `runs/<RUN_TS>-<loop>.md` are write-once per-run logs that nobody reads back; `ledger.md` is a 1-line-per-run index the runner writes; `python3 ~/.claude/skills/todo-collect/todo_queue.py summary` is the 20-line on-demand view. All generated; do not hand-edit.
4. **Approval**: `/todo-approve` (interactive, 4 candidates per AskUserQuestion) — or, when `surfaces.queue_surface` is `slack-self-dm`, one self-DM per candidate answered with a reaction (Phase 2 of the 2026-09 redesign).

Do NOT `browse(tags=todo)` at every session start — context cost without payoff; the channels above cover it.

## Advancing and closing

States are minimal: a TODO **exists (open)** or is **deleted (done / obsolete)**. No in-progress flag — sessions and branches embody in-progress; a status flag only goes stale.

- **Starting**: 「TODO の X やろう」 → pull the record; its close condition + first step ARE the working contract.
- **Progress**: dated status line in TODO.md (existing pattern: `Status 2026-07-05: …`) / `revise(id)` for memory todos.
- **Closing is part of done-reporting**, not an afterthought: when work completing a TODO is verified, delete it in the same turn — TODO.md entry in the resolving commit; memory todo via `forget(id)`. **Evidence-based auto-close**: completion machine-verified (PR merged, file exists, probe passes) → forget WITHOUT asking + one receipt line ("完了確認 → todo forget: <summary>"). Not machine-verifiable → propose, apply on approval.
- **Backstop**: weekly `/todo-reconcile`. Due dates within 7 days get flagged there. Minute-grained reminders are Calendar/Reminders territory — memory todos carry only loose dates.

## Collector (`/todo-collect`) — external capture channels

Two-phase capture: **raw capture** happens in whatever tool the user is in, via that tool's native zero-friction gesture; **normalization** (draft the close condition, attach provenance, dedup, route) happens asynchronously in the collector. The user never fills in the contract by hand.

Config: `~/.claude/todo/sources.yaml` (cookbook-managed) merged at runtime with `~/.claude/todo/sources.local.yaml` (unmanaged — work sources live here, never in the public repo). Per-source schema: `name / class / adapter / query / sink / enabled`.

**Source classes**:

- `explicit` — the user made a deliberate mark → auto-`remember` + receipt in ledger. Examples: Slack self-DM, 📌 reaction, Slack bookmark, Google Tasks, Notion inbox DB.
- `inferred` — extraction guesses intent → **candidates only**, written after user approval (batched AskUserQuestion or ledger candidates section). Examples: Claude Code transcript deferral mining (「あとでやる」 that never got a receipt), action items in calendar-linked Notion meeting notes.

**Dedup**: by provenance (Slack permalink / task id / event id / transcript position), so re-sweeps never duplicate. Sources are never mutated (no auto-complete of Google Tasks, no un-bookmarking).

**Sink routing = sensitivity routing**: each source declares its sink. Work sources (Mercari Slack, work calendar) → `memory-work`; personal sources → `ai-memory`. This is the same egress rule as `knowledge-persistence.md` "local is NOT air-gapped" — a work capture in personal ai-memory is a violation, not a convenience.

**Runtime constraints** (2026-08-17, measured on sh1-cloud with claude 2.1.233): a headless `claude -p` **can** reach the claude.ai connectors — the Slack tools load through `ToolSearch` and `slack_search_public("is:saved")` returned rows on two consecutive probes — so the connector is no longer the blocker for unattended work-source collection. Do not re-derive that claim from an older note; re-probe it if a run behaves as if the tools are missing. What headless still cannot do is host-specific: `gws` answers 401 (`invalid_rapt`) until someone re-auths in a browser, the `remind` CLI is macOS-only (so the Reminders mirror runs on air only), and ai-memory is not registered on sh1-cloud (so the personal store is enumerable only from a personal host). The store side is settled: memory-work is a single-node ES on `sh1-cloud` behind an OIDC proxy, reachable from every work host (the LAN-scope constraint died with the air-local store, retired 2026-08-17).

**Cadence**: the work half runs unattended on sh1-cloud — `todo-collect.timer` daily 07:23 JST, `todo-reconcile.timer` Mon 08:13 JST, both from zp-SHIN's `mercari-claude-todo` cookbook (runner + prompt design: `~/.claude/docs/claude-cli-headless.md`). The personal half (Reminders mirror, ai-memory sinks, Google Tasks) still runs interactively, pairing naturally with `/morning-triage`. Two rules make the unattended runs honest: they never write `inferred` captures (no approver is present — candidates go to `candidates.jsonl` and wait for `/todo-approve` or the configured approval surface), and every source they cannot reach is recorded as `unswept` with a reason rather than as zero. The runner verifies each cycle structurally: the run log carries the run id, `candidates.jsonl` was regenerated by that run (meta.run) and obeys the enum contract, an unparsable queue is rolled back to `.prev`, and the claimed 新規 + disposition count matches the `remember` calls in the transcript; reconcile additionally proves by sha256 that its session never touched the queue.

## Queue — `~/.claude/todo/` layout (2026-09 redesign)

The single append-only `ledger.md` (2061 lines / 188 KB by 2026-08-30, ~100 lines per collect run, the approval queue buried inside its prose) was split into state and history. State is O(open) and regenerated wholesale; history is write-once and never read back by a loop.

| Path | Kind | Writer | Size |
|---|---|---|---|
| `candidates.jsonl` | state — the approval queue: line 1 meta, then one candidate per line | collect only, via `todo_queue.py filter` (tmp + atomic replace). Never Write/Edit by hand or by a model | O(open) |
| `runs/<RUN_TS>-collect.md`, `runs/<RUN_TS>-reconcile.md` | history — write-once run log, run id in the first heading | the run's own session; nobody reads it back | 1 run = 1 file |
| `runs/0000-legacy-ledger-<first>_<last>.md` | history — the pre-split ledger, moved once by `init` | migration | fixed |
| `ledger.md` | index — one line per run: `utc \| loop \| run id \| ok\|fail(class) \| summary \| run log` | the headless RUNNER (a model never writes it; interactive runs leave no line) | 1 run = 1 line |
| `tmp/<RUN_TS>-sweep.json`, `tmp/<RUN_TS>-config.json` | hand-off — the session's structured sweep and the merged config, inputs of `filter` | collect session | per run |
| `stores.json` | state — store-level open counts in the 3-valued vocabulary + `air_pending_forget` | reconcile only | O(store) |
| `prs.json` | state — the open reconcile PRs (`prs: null` + `error` when gh failed, never an empty list) | reconcile runner | O(open PR) |
| `summary.txt` | view — the 20-line `todo_queue.py summary`, refreshed by the runner on every path (skip / DISABLED included) | runner | fixed |

**Helper**: `python3 ~/.claude/skills/todo-collect/todo_queue.py` — `init` (idempotent layout + one-time migration) / `validate --sweep|--queue` / `filter` / `summary`. It is python3 (stdlib only) rather than a sibling of `remind_sync.rb` because the headless runner's systemd PATH resolves `/usr/bin/python3` and no rbenv shim. It never talks to a memory store; every store read/write stays with the skill.

**Canonical provenance keys** (dedup is an exact string match on these; the key sits on the first line of every todo and disposition record as `key=<key>`): Slack `slack:<channel_id>/<ts>` (from the permalink's `p<digits>` — the workspace hostname is deliberately not part of the key, two hostnames were in circulation), Notion `notion:<page_id>#<block|idx>`, transcript `transcript:<session_id>:<line>`, Reminders `reminders:<externalId>`, Google Tasks `gtasks:<list>/<task>`.

**3-valued vocabulary is an enum, not prose**: `sources[].status ∈ swept|unswept|truncated` and `*_enum.state ∈ complete|truncated|unreached`; `truncated` requires `remaining` (int or `"unknown"`), `unswept`/`unreached` require a `reason`. `validate` rejects anything else and the runner re-checks with jq, so "unreached rounded down to 0" is unrepresentable.

**Aging** (`max_age_days` on an inferred source, `queue.ttl_days` globally): a candidate whose ORIGIN date (message / meeting date, not the day it was seen) is older than `max_age_days` never enters the queue; one that sat in the queue longer than `ttl_days` since `first_seen` is expired (an `expired` disposition is written). Both are listed one per key in the run log. This is the 2026-08-18 rule "Slack saved 由来で起票 1 か月超の依頼系は TODO 化しない" turned from prose into config — it retired 28 of the 35 candidates that had lingered for a month.

## Dispositions — approve / reject / snooze / never / done / expired / revive

The store of truth for a decision is the memory store, not a local file (a local file cannot be written from the other host, so a rejection made on the laptop would be re-proposed by the box the next morning). **approve** is the todo record itself. Every other decision is an append-only `todo-disposition` fact:

```
todo-disposition <kind> key=<key> written_at=<ISO>[ until=<YYYY-MM-DD>][ thread_key=<tk>][ announce=<channel>/<ts>]
<one line of reason or title>
```

tagged `['todo-disposition', '<kind>', '<source>']`, written to the SAME sink as the candidate's source. Rules: append-only and latest-`written_at`-wins per key (no `forget`/`revise`, so the provenance boundary between the box's service account and the laptop's operator identity never bites); a record carrying `thread_key=` hides the whole thread (`never` writes it, `reject` does not); `done` applies to explicit and inferred captures alike; a `revive` cancels the hide. The tag filter on the server is an exact keyword match, so `todo-disposition` records never leak into a `browse(tags:"todo")` enumeration.

**`done` is mandatory on every close path.** Slack sources are immutable (a saved item or a 📌 stays), so once a todo is forgotten its key falls out of the todo set and the next sweep would re-propose it — the `done` record is the only thing that stops that. The three paths that forget a todo — `/todo-reconcile` Step 4, `/todo-approve --undo`, and `remind_sync.rb`'s close A (reminder completed) — each write `todo-disposition done key=<key> … reason=<evidence>` in the same turn.

`filter` applies dispositions only when their enumeration is `complete`; on `truncated`/`unreached` it skips the disposition and snooze filters and says so in meta (`filters_skipped`) — showing too much beats hiding a live candidate.

## Run logs and index

A run writes exactly one file, `runs/<RUN_TS>-<loop>.md`, whose first heading carries the run id the runner injected; the runner greps that id (and, for collect, the `remind` / `ai-memory` unswept tokens) as its proof the session did the work. The runner — never the model — appends the `ledger.md` index line after classifying the cycle, so an index line is evidence, not a claim. Interactive runs have no runner and leave no index line; `summary` derives history from `runs/` filenames.

## Apple Reminders integration (remind CLI)

真実源は変わらず memory store（ai-memory=個人 / memory-work=work）。Apple Reminders は 2 役を担う連携ストア:

- **surface (mirror)**: open な memory todo を専用リスト（default "Claude"）に 1:1 でミラー — Siri / iOS / watch から見え、完了にできる面
- **capture 入口**: ユーザーが Siri / iOS で作った reminder を `/todo-collect` の `apple-reminders` adapter（explicit class）が memory に正規化取込

**リンク機構（stateless）**: reminder 側は notes 末尾行トークン `[ai-todo:<memory-id>]`（= memory item にリンク済みの印）、memory 側は content 内の `reminders:<externalId>`（capture 由来の provenance）。状態ファイルは持たず、毎回 2 つのダンプ（`remind --dump` JSON / memory dump JSON）から plan を導出する。

**sync 5 規則**（R = 対象リスト群の全 reminder incl. completed、M = open memory todos）:

1. **capture_candidate**: r 未完了・トークン無し・どの m からも未 ref・due が horizon 内（既定 14 日、`capture.due_horizon_days`、負値で無効 — 先の予定は Reminders 自身が通知を担う）→ capture 候補（collector の正規化フローへ。**sink はソース定義の既定値** — 混在リストは内容で work/personal を routing する）
2. **annotate**: トークン無しだが open な m が r.externalId を ref → notes に `[ai-todo:m.id]` を追記（収束ステップ）
3. **create_mirror**: reminder 由来でない open な m にミラー r が無い → mirror リストに add（notes にトークン）
4. **forget (close A)**: r 完了済み・リンク先 m が open → memory forget（reminder 完了 = 機械的証拠、evidence-based auto-close）
5. **complete (close B)**: r 未完了・トークンの id が M に無い（memory 側で forget 済み）→ reminder を complete

fixpoint: apply 2 回で収束、3 回目は全規則 0 件（冪等）。

**mirror 内容ポリシーと egress 境界**:

| store | policy | reminder に出る内容 |
|---|---|---|
| ai-memory（個人） | `full` | title = content 先頭文（接頭辞除去・100 文字打切）、notes = 完了条件行 + 最初の URL + トークン行 |
| memory-work（work） | `title-link` | title 同様、notes = 最初の URL + トークン行のみ（本文を iCloud に出さない） |

public default（`sources.yaml` の `mirror:`）は ai-memory/full のみ。work store のミラーは zp-SHIN overlay の `sources.local.yaml` で opt-in（title-link 固定）— iCloud は第三者 egress 面であり、`knowledge-persistence.md`「local is NOT air-gapped」と同じ判断基準を適用する。due は content が `期日: YYYY-MM-DD[ HH:MM]` にマッチした時のみ `--due` で付与。

**実行タイミング**: `/todo-collect` Step 6（日次、interactive session 冒頭）。実装は todo-collect skill ディレクトリの `remind_sync.rb`（plan/apply CLI）+ `remind` CLI（`--dump` / `--complete` / `--annotate` / `--mklist`）。
